# Підсумок вимог Moodle до курсової

Джерела: сторінки Moodle ID 455875 (основні вимоги) та ID 455874 (рекомендована структура); курс ID 3729. Текст отримано з авторизованого перегляду 2026-11-22.

## Перевірені обов'язкові вимоги

- Один наскрізний ІТ-проєкт у всіх розділах.
- Практичні результати: власні аналізи, розрахунки, схеми, графіки й обґрунтування, а не переважно теорія.
- Microsoft Project: календарне, ресурсне та вартісне планування; обов'язковий файл `.mpp` із графіком, ресурсами, бюджетом, Baseline та даними моніторингу.
- Jira: організація завдань і моделювання Agile-процесів.
- Можна моделювати фактичні дані для моніторингу, але всі припущення треба явно назвати.
- Узгодити між собою план, бюджет, ресурси, фактичні дані, відхилення й управлінські рішення.
- Належно цитувати використані джерела.

## Рекомендована структура

### Вступ
Актуальність; мета й завдання; очікувані результати; практична цінність.

### Розділ 1. Ініціація та організаційне обґрунтування
1.1. Концепція/статут, бізнес-потреба, SMART-мета, результати, обмеження, критерії успіху, Project Charter.
1.2. Зацікавлені сторони, Stakeholder Register, Power–Interest, функціональні та нефункціональні вимоги, User Stories, Acceptance Criteria.
1.3. Порівняння Waterfall/Scrum/Kanban/гібридного підходу; обґрунтування методології; життєвий цикл; Product Backlog; команда, ролі, RACI, комунікації.

### Розділ 2. Планування змісту, строків, ресурсів і вартості
2.1. Scope/Scope Statement; WBS; Work Packages/Milestones; залежності й тривалості; календар; MS Project і діаграма Ганта.
2.2. Ресурси, їхні ставки/вартість, призначення, завантаження та перевантаження; трудомісткість; бюджет; оптимізація; Baseline.
2.3. Проєкт Jira; Scrum- або Kanban-дошка; Epic, User Story, Task, Sub-task; пріоритети/статуси/виконавці; Sprint Backlog, якщо Scrum.

### Розділ 3. Моделювання виконання, моніторинг та оцінювання
3.1. Класифікація ризиків; Risk Register; ймовірність/вплив і матриця; реакції; критерії якості/Definition of Done; Change Request та вплив зміни на зміст, строки, бюджет, якість.
3.2. Моделювання частини виконання; Jira-спринт/дошка; фактичні значення в MS Project; план-факт, відхилення від Baseline; EVM: CPI/SPI; доречні Agile-метрики; Project Status Report.
3.3. Причини відхилень; коригувальні дії; досягнення цілей; приймання; Project Closure Report; Lessons Learned/Retrospective; очікувана цінність.

### Висновки, джерела, додатки
Висновки мають узагальнювати практичні результати й обґрунтування рішень. У додатки виносяться великі плани, матриці, реєстри, звіти MS Project і докази роботи в Jira.

## Критерії відповідності для подальшої перевірки

| ID | Критерій | Майбутній доказ |
|---|---|---|
| M-01 | Один проєкт у всіх артефактах | Єдиний Project Charter і узгоджений опис продукту |
| M-02 | Власна практична робота | Розрахунки/таблиці/схеми з поясненням методу |
| M-03 | План і ресурсна модель | `.mpp`, календар, WBS/Gantt, ресурси й ставки |
| M-04 | Вартість і Baseline | Бюджет у `.mpp`, збережений Baseline |
| M-05 | Jira | Дошка та набір власних Epic/Story/Tasks (або чесно позначена модель/макет, якщо доступу нема) |
| M-06 | Ризики/якість/зміни | Risk Register, критерії якості, приклад Change Request |
| M-07 | Узгоджений моніторинг | Фактичні дані з поміткою «модель», CPI/SPI та план-факт |
| M-08 | Завершення й висновки | Статус-звіт, закриття, Lessons Learned, висновки |
| M-09 | Академічна доброчесність | Бібліографічні посилання й перевірювані джерела |

## Обмеження збору

Не переглядати та не завантажувати подання інших студентів або індивідуальні завдання на перевірку академічної доброчесності. Не проходити тести та не надсилати файли в Moodle. Точний формат титульної сторінки й обсяг курсової цими двома сторінками не встановлено — його треба знайти в робочій програмі/методичці або уточнити у викладача.
