# AGENT5_ACADEMIC_CONTRACT.md — академічний стандарт підготовки курсової №46

Цей контракт — адаптація наданого власником файлу **«Універсальний_промпт_курсова_робота.txt»** до теми №46 і конкретних вимог Moodle. Оригінальний персональний файл **не публікується**; тут зафіксовані операційні правила для Agent 5 та його чотирьох дочірніх оркестраторів.

## 1. Ієрархія вимог

**Перша черга:** актуальні методичні вимоги викладача/Moodle до «Управління ІТ-проєктами», передусім `docs/structure-and-requirements.md` та `docs/coursework-source-pack/README.md`.  
**Друга черга:** цей універсальний академічний контракт.  
**Третя черга:** редакторські вподобання, історичні чернетки й приклади.

При розбіжності (наприклад, універсальна «теоретична» структура проти конкретних **трьох практикоорієнтованих розділів**) використовуй вимоги Moodle. Не видавай попередню чернетку за перевірену роботу.

## 2. Вхідні дані та невідомі реквізити

- Тема: «Управління ІТ-проєктом створення корпоративного порталу підприємства».
- Дисципліна: «Управління ІТ-проєктами».
- Спеціальність: 122 «Комп'ютерні науки».
- Достовірні дані про студента / університет можна використовувати лише з уже наданих джерел, попередньо перевіривши, що вони придатні для публічного репозиторію.
- **Не вигадуй:** ім'я керівника курсової, кафедру, форму титульного аркуша, сторінковий норматив, реквізити неотриманих методичок та реальне підприємство.
- Для відсутніх полів — явні заповнювачі `[УТОЧНИТИ]`; надішли список точкових питань після створення придатної до перевірки чернетки.

## 3. Дослідницький дизайн (до написання)

1. Розбери термінологію, актуальність, предметну область і практичне завдання управління корпоративним порталом.
2. Визнач об'єкт, предмет, мету, завдання, методи й очікувані результати.
3. Зістав методології Waterfall, Scrum, Kanban та гібридний підхід, аргументуй вибір для кейсу.
4. Проведи проблемно-тематичний аналіз досліджень: управління вимогами, ризики, WBS, Agile, контроль вартості, EVM, зацікавлені сторони, якість, тестування, цифрові корпоративні платформи.
5. Визнач, які результати мають статус реального артефакту, які — навчальної моделі, а які поки недосяжні. **Не заявляй «наукову новизну» без підстав.**
6. Створи логічний план трьох розділів, узгоджений із Moodle, перш ніж генерувати основний текст.

## 4. Систематичний пошук та відбір літератури

### Орієнтовні цілі, якщо методика не каже інакше

- Для типових 25–35 сторінок основного тексту: **орієнтовно 30–40 релевантних перевірених джерел**, для складніших робіт 40–60; якість важливіша за кількість.
- Як орієнтир **60–70% джерел за останні 5 років**, бажано 2022–2026 для роботи 2026 року, якщо це підходить темі. Старіші фундаментальні стандарти допускаються.
- Орієнтовний баланс українських та іноземних досліджень **50/50**, коли наявність джерел дозволяє. Це **не норматив**, якщо кафедра його не встановлювала.
- Якщо перевірених матеріалів менше, чесно вкажи дефіцит; не доповнюй список вигаданими статтями.

### Порядок пошуку

1. Створи 5–10 ключових понять українською та англійською із синонімами (IT project management, corporate portal, stakeholder management, requirements prioritization, WBS, Agile, EVM, UAT, project risk та ін.).
2. Підготуй пошукові запити з `AND / OR / NOT`, точними словосполученнями, фільтрами року й типу публікації.
3. Шукай у релевантних міжнародних і українських наукових джерелах: Scopus/WoS (за дозволеним доступом), SpringerLink, ScienceDirect, IEEE Xplore, ACM DL, Wiley, Taylor & Francis, категорії А/Б, НБУВ, українські університетські репозитарії.
4. Для знаходження й перевірки метаданих застосовуй Google Scholar, Crossref, OpenAlex, DOAJ, ORCID; **не плутай індексацію в пошуковику з індексацією у Scopus/WoS**.
5. Для норм і технічних вимог долучай офіційні першоджерела: PMI, Atlassian, Microsoft, ISO, OWASP, стандарти й закони за релевантністю та з урахуванням прав доступу.
6. Відбирай за назвою, анотацією, ключовими словами, датою, DOI, повним текстом і реальною предметною релевантністю; вилучай дублікати.
7. Для найбільш релевантних праць перевіряй попередні посилання та пізніші цитування, поки не буде достатнього корпусу доказових джерел.

### Верифікація бібліографії

Для кожної позиції фіксуй: автори, повна назва, журнал/книга/збірник, рік, том, номер, сторінки/номер статті, DOI/постійний URL, мову, дату перевірки, факт доступу до повного тексту, статус індексації **зі вказанням джерела підтвердження**.

**Не вигадуй** DOI, ISBN/ISSN, категорію Б, квартиль, Scopus/WoS, том, випуск, сторінки, результати досліджень. Якщо DOI є, це саме по собі **не доводить** індексацію журналу. Перевіряй офіційні Scopus Sources, Clarivate Master Journal List або чинні переліки МОН України, якщо заявляєш такий статус.

Джерело без повного тексту познач як `ABSTRACT_ONLY`, не приписуй йому неперевірені результати.

## 5. Аналіз повних текстів та журнал джерел

Створи `05-coursework/source-matrix.csv` з полями:

`id,authors,year,title,publisher_or_journal,doi,url,language,full_text_access,indexing_claim,indexing_evidence,methods,results,limitations,practical_value,used_in_section,verified_on,verification_status`.

Для основного джерела фіксуй мету, метод, результати, обмеження, аргументи, практичне значення, відповідний розділ і **сторінки чи конкретні фрагменти** для істотних тверджень. Аналізуй підходи в тематичних групах, виявляй суперечності, не роби простий переказ кожної статті.

## 6. Офіційна структура цієї курсової

Застосовуй **не шаблонні заголовки універсального промпту**, а фактичну структуру Moodle:

- **Титульний аркуш, зміст, вступ.**
- **Розділ 1. Ініціація та організаційне обґрунтування:** концепція, Project Charter, SMART, Stakeholder Register, Power–Interest, вимоги, User Stories, критерії приймання, методологія, backlog, RACI, комунікації.
- **Розділ 2. Планування змісту, строків, ресурсів і вартості:** Scope, WBS, мілістоуни, MS Project/Gantt, ресурси, завантаження, ставки, бюджет, Baseline, організація виконання та Agile-роботи у Jira.
- **Розділ 3. Моделювання, моніторинг та оцінювання:** Risk Register/Probability–Impact, якість, зміни, моделювання факту, PV/EV/AC, CPI/SPI, статус-звіти, Agile-метрики, завершення, Lessons Learned.
- **Висновки, перевірена бібліографія, додатки** з реально доступними доказами.

Кожне завдання зі вступу має бути розкрите в тексті й мати відповідний підтверджений результат у висновках. У всіх розділах один сценарій та узгоджені цифри.

## 7. Академічний стиль і доброчесність

- Пиши українською, природним науковим стилем, конкретно, без води й повторів; уникай штампів на кшталт «у сучасному світі», «слід зазначити», механічних переходів і надмірного довгого тире.
- Відокремлюй дані інших авторів, власні розрахунки, навчальні припущення та гіпотези.
- **Не вигадуй** опитувань, експериментів, статистики підприємства, User Acceptance Testing, реального використання Jira/MS Project, успішних перевірок і даних Baseline.
- Навчальне моделювання плану/факту допускається, якщо явно описані вхідні припущення і методика обчислень.
- Перевір відтворюваність розрахунків і відповідність висновків даним. Не додавати порожніх абзаців заради обсягу.

## 8. Цитування та оформлення джерел

- Якщо методичка не встановлює іншого — **ДСТУ 8302:2015**.
- Текстові посилання `[7]` і `[7, с. 45]` лише за перевіреної відповідності нумерації/сторінки.
- Для кожного посилання перевір, що джерело існує, містить потрібне твердження, а точні цитати не спотворені; кожне джерело у списку використано.
- Не включай дублікати, неперевірені записи, фальшиві DOI, вигадані номери сторінок та джерела для «набору кількості».

## 9. Фінальний редагований DOCX і PDF

Основний результат: `05-coursework/Kursova_robota_korporatyvnyi_portal.docx` — сумісний із **Microsoft Word 2010**; за можливості `05-coursework/Kursova_robota_korporatyvnyi_portal.pdf` для перегляду. Якщо кафедра вимагає інакше, змінюй відповідно до реальних методичних рекомендацій.

**Типові параметри за відсутності інших вимог:**

| Параметр | Значення |
|---|---|
| Формат | A4, книжкова орієнтація |
| Шрифт | Times New Roman 14 pt |
| Інтервал | 1,5 |
| Абзац | відступ 1,25 см |
| Вирівнювання | по ширині |
| Поля | ліве 3 см; праве 1,5 см; верхнє/нижнє по 2 см |
| Нумерація | арабська, титульна сторінка без видимого номера |
| Основний текст | орієнтовно 25–35 сторінок, якщо методика не каже інше |

Створи реальні Word-стилі заголовків, **автоматичне поле TOC** (або явно задокументоване обмеження засобу), автоматичну нумерацію сторінок, коректні розриви, таблиці як **редаговані Word-таблиці**, підписи й посилання на кожну таблицю/рисунок/формулу. Формули мають бути редагованими настільки, наскільки це підтримує обраний інструмент. Не перетворюй таблиці на картинки.

У титулі використовуй лише підтверджені реквізити; невідомі поля познач `[УТОЧНИТИ]`. Додатки мають містити змістовні перевірені матеріали, а не декоративні сторінки.

## 10. Технічний, науковий і візуальний аудит

Після формування DOCX:

1. Перевір, що файл реально існує, **відкривається**, редагується, не має пошкодженої структури, випадкових порожніх сторінок чи надламаних стилів.
2. Перевір ієрархію заголовків, зміст, сторінки, таблиці/підписи, формули, поля, заголовки внизу сторінки, посилання на додатки.
3. Звір об'єкт/предмет/мету/завдання з виконаними результатами; переконайся, що розділи 1–3 і висновки узгоджені.
4. Автоматизовано і вручну звір бібліографію (автори, назви, DOI, рік, номера цитувань) та істотні твердження.
5. Конвертуй DOCX у PDF, **якщо інструмент доступний**, візуально оглянь титул, зміст, таблиці, рисунки, бібліографію й сторінки, виправ і повтори. За відсутності конвертера чесно запиши `NOT_VERIFIED`.
6. Звір пояснювальну записку з матрицею `docs/traceability.csv` та `docs/evidence-manifest.md`: не описуй нестворене як виконане.

Не оголошуй результат готовим тільки тому, що файл згенеровано.
